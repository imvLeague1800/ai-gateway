# Qwen 与 Gemma 4 的 256K 对照测试

> 执行结果见 [qwen-gemma-256k-test-results.md](qwen-gemma-256k-test-results.md)。

在当前仓库的隔离测试环境执行对照测试。**将 `.15` 的 Qwen3.6 35B 和 `.16` 的 Gemma 4 都改到 256K 上下文，并统一关闭 thinking。** 只修改两台测试引擎及对应的隔离网关配置。生产配置、`.bak`、Dashboard、Auto 路由规则和模型副本数量均不在本轮范围内。

## 配置与测试

1. **两台都设为 256K。** 将测试引擎的 `max_model_len` 和隔离网关对应模型的 `max_context_tokens` 都设为 `262144`。启动后核实实际生效值。每次测试统一预留 **1,024 个输出 token**，用各模型自己的 tokenizer 计算渲染后的完整输入，确保 `输入 token + 1024 ≤ 262144`。如果某台启动失败或无法完成近上限请求，记录失败阶段、最大实测成功长度（如有）和错误。
2. **两台都关闭 thinking。** 使用各模型和服务版本支持的参数显式关闭，并通过渲染后的模板或服务端生效参数确认。响应中缺少 reasoning 字段不足以确认生效。无法确认时标记为“未验证”。
3. **用显式模型入口公平对照。** 确认 Qwen 请求落到 `.15`，Gemma 4 请求落到 `.16`。使用相同题目、消息、工具定义、`temperature=0` 和流式调用方式。先测单并发，再测两边共同支持的并发档位。每个场景至少重复三轮，交替运行两模型，保留失败样本。覆盖**独立代码问答、多轮编码 Agent、长文档/RAG、256K 边界**。Agent 区分冷首轮和稳定前缀续轮，RAG 区分同文档追问和召回内容变化。256K 边界用单并发逐步升长。

### 网关行为验证清单

每项填写“通过 / 失败 / 未验证”，附请求 ID、实际后端和观察结果。

- [ ] 两台引擎和网关的 256K 配置均生效，thinking 均已关闭。
- [ ] 显式模型映射正确，流式响应和工具调用可用。
- [ ] 近上限请求通过，或记录资源限制。超限请求被网关拒绝且未派发。
- [ ] 达到并发上限后，排队、超时或拒绝符合配置。已完成请求释放容量。
- [ ] 排队取消和流式断开后，检查队列项、引擎状态和预留额度是否恢复。
- [ ] 稳定前缀续轮和 RAG 内容变化的缓存表现有记录。
- [ ] 显式模型不可用时的行为已验证，并标明使用实机、mock 还是隔离故障注入。
