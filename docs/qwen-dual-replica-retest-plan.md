# 双 Qwen 路由补测与可复用测试集计划

执行对象为另一位 agent。本计划由文档作者交接，部署和压测由执行 agent 按下述步骤开展。目标是在同条件下完成 `power_of_two` 与 `cache_aware` 的验收，并留下可用于升级回测的版本化测试资产。

## 1. 基线与执行准备

- 复用 [原测试计划](qwen-dual-replica-test-plan.md) 的两台独立 Qwen 部署、256K 上限、关闭 thinking、最多 1,024 输出 token、显式模型入口及 Gemma 回退步骤。先核对当前实机状态，再临时切换 `.16`，保存当时的 Gemma 配置。测试完成恢复 Gemma，并验证原入口。
- 保存 [前轮结果](qwen-dual-replica-test-results.md) 和原始记录，追加本次结果。正式补测前完成统计脚本与数据集校验。用 mock 验证时间、缓存聚合、流中断分类和评分计算。
- 两策略使用相同 Router 镜像 digest、worker 配置和健康检查参数。性能对照保持前轮已校准的缓存参数 `cache_threshold=0.3`、`balance_abs_threshold=2`、`balance_rel_threshold=1.2`。如版本或环境变化导致必须调参，先另做校准轮，冻结后重新跑完整配对回放。
- 所有测试负载通过唯一 Router 入口。记录实际负载信号。前轮 `/get_load` 为 404，因此使用本地在途计数，直连引擎的背景流量不可用于制造可见拥堵。

## 2. 测试集必须长期保存

由执行 agent 创建 `benchmarks/router/`，将它作为可审查、可版本化的回测资产。先导入前轮合成用例，随后加入真实 Agent 用例。正式验收使用冻结的测试集版本。

| 资产 | 内容与要求 |
| --- | --- |
| `manifest.json` | 数据集版本、schema 版本、来源、用途、用例数量、生成器版本和随机种子、文件 SHA-256。区分合成用例、真实记录和人工改编用例。登记来源允许的内部使用范围。 |
| `cases.jsonl` 及必要的附件 | 稳定的 case ID、场景、完整 messages/tools、预期文本或工具参数、评分方式、TTFT 和完成时间预算。代码任务附固定仓库快照标识、可重建的最小工程或 fixture，以及可执行测试。大文档保留内容或可复现生成器和哈希。 |
| `sessions.jsonl` | session ID、步骤 ID、父步骤、实际回复与工具结果、续轮间隔、会话开始偏移和请求序列。记录并行分支。保留完整前缀与上下文增长关系。 |
| `profiles.json` | 轻载/高载到达节奏、40/30/30 合成比例、真实会话比例、会话数、重复前缀分布、随机种子和采样方式。保存独立会话数量及每会话轮数。 |
| 回放和评分程序、使用说明 | 复用现有 harness，保存为仓库中的可维护脚本，说明准备、回放、评分及报告命令。保留原始时间戳、计量精度、百分位算法和失败定义。 |

真实样本来自公司授权使用的 Agent 会话。用稳定占位符处理密钥、内部地址和身份信息，保留工具结构、代码逻辑及重复前缀关系。保存变换规则并验证变换后的用例。尚无真实会话时完成其他补测，将真实 Agent 验收标为待补，避免用合成记录替代真实记录的来源声明。

数据集分为校准集和冻结验收集，同一原始任务及其改写只放一边。至少 20% 的真实会话留给校准，正式调参结束后固定其余验收会话。参数和预算在验收前冻结。发现用例或评分器有问题时升数据集版本，并对两策略重新配对，保留旧版结果。

每次运行另存唯一 run ID 的原始请求、响应或响应引用、引擎指标、Router 决策、版本与配置快照、评分及聚合结果。记录数据集哈希、Git revision、机器与镜像、模型和 tokenizer/template 哈希。大文件或敏感结果可放内部持久存储，在仓库登记可访问的位置、哈希及保留方式。现有 `.verification/` 被 Git 忽略，须将有长期价值的测试输入和运行证据纳入上述保存流程。

## 3. 补测场景与样本

### 稳定前缀及混合高载

- 稳定前缀继续测 16K RAG 和较长 Agent 上下文，按会话配对记录冷首轮、续轮实际副本和缓存数据。每组至少 20 个完整会话，重复 3 组。两策略的原始用例、输出预算与到达节奏一致。
- 混合高载继续用前轮的 3.0 req/s 作为起点，独立保存该 profile。每种策略每组至少 **300 个计分请求**，做 **3 组配对回放**，每策略高载合计至少 900 个请求。用相同 profile 做轻载 1.5 req/s 对照。确认正式窗口内确有排队，若当前环境已无高载特征，先校准请求率并冻结，再开始配对测试。
- 各轮使用独立前缀命名空间，开始前排空旧请求、重建 Router 前缀历史，执行相同预热。若引擎缓存不能清空，使用 token 长度和结构等价的中性前缀标记，交叉分配到两策略并记录差异。保存实际渲染 token 数。避免策略名固定绑定某种标记。
- 策略运行顺序交替。正式窗口以预先生成的会话开始时间回放，续轮必须等待父步骤完成，再加冻结的思考/工具间隔。同时保存计划到达与实际发送时间。并发分支遵从会话依赖。各策略使用同一个会话到达计划，分别报告实际请求节奏。
- 持续以 1 秒间隔采集每副本 running、waiting、KV 使用率、缓存计数和抢占，保留窗口结束后的排空数据。短请求、冷请求、续轮分别报告尾延迟。先记录背景空载，出现外部请求时标记污染轮并重跑配对。

### 真实 Agent 回放

- 至少准备 **20 个独立的真实多轮任务**，每个至少 3 个模型调用，覆盖代码修改、调试、工具调用及较长上下文。分配校准与验收集合后，验收会话至少重复 3 组配对。报告真实前缀长度，保留短前缀任务。
- 请求级性能回放使用冻结的历史请求、真实 assistant 消息和工具结果，保持下一轮输入在两策略间可比，标明历史回放模式。另用至少 5 个带可执行测试的任务运行闭环 Agent，真实执行工具并让上下文自然增长，记录任务完成时间、工具轮数和测试结果。闭环回放允许路径变化，单独统计。
- 保存较长输出任务。1,024 输出上限触发截断时记为不完整。若任务确需更长预算，单独建立两策略一致的长输出 profile 并冻结，不与原 profile 混算。

### 故障与热副本

- 统一健康检查为 **间隔 5 秒、失败阈值 2、成功阈值 2**，并记录单次健康检查超时参数，两个策略保持一致。两策略、两个被停副本各重复 3 次。计时从发出停止动作前开始，持续观测到故障摘除及恢复，避免等流超时后才读取状态。
- 记录停止时间、首次探测失败、Router 标不健康、新请求实际落点、在途流结束或中断、引擎恢复健康和 Router 重新接单时间。HTTP 200 响应头之后流中断计为失败。
- 故障摘除目标为 **20 秒内**，恢复目标为引擎 `/health` 恢复后 **20 秒内**重新可接单。若探测阻塞导致超时，记录失败与原因。摘除后发送 20 个探针，核实都成功落到健康副本。完整的故障窗口失败率另外报告。
- 保留热副本双向改派验证。增加“继续等待热副本”的独立强制选址对照，与自动改派在等价背景负载下配对，比较实际 TTFT 和完成时间。该对照作为阈值分析，单独标记实验入口。

## 4. 修正指标口径

| 指标 | 统一算法 |
| --- | --- |
| 实际缓存命中 token 占比 | 窗口内两引擎 `hits` 增量之和 / `queries` 增量之和。计数器重启或清零时切分窗口。并发聚合指标只归因到副本和窗口。 |
| 缓存命中请求比例 | 仅在有请求级证据时，计算命中 token 大于 0 的请求数 / 有完整缓存观测的请求数，同时报告观测覆盖率。请求命中比例中位数必须标明“中位数”。 |
| 同副本续轮比例 | 有完整副本归因的续轮中，与父轮同副本的次数 / 可归因续轮次数。与实际缓存命中分开计算。 |
| TTFT、完成时间 | 客户端单调时钟，首个实质 content/tool 增量及完整流结束。保存原始值。P50/P95/P99 用相同算法，按场景、阶段、负载及轮次列样本数。失败样本单独统计，不能当成成功低延迟。 |
| TTFT 达标率 | 成功、质量通过且 TTFT 在预算内的请求 / 该批全部请求。保留前轮预算作可比列，QA 2 秒、冷 Agent/RAG 10 秒、续轮 5 秒。 |
| 完整延迟达标率 | 成功、质量通过且 TTFT、完成时间都在预算内的请求 / 该批全部请求。各场景完成时间预算在校准集上确定并冻结，正式验收禁止回调预算。 |
| 固定窗口达标请求每秒 | 在固定发送窗口接纳的请求中，最终满足上述条件的数量 / 预先固定的窗口时长。明确采用 TTFT 或完整延迟预算，分别给两列。所有请求最终状态仍需等待收齐。 |
| 持续处理能力与排空 | 报告完成数、请求率、实际到达率、窗口内队列趋势及排空时长。若排队持续增长，固定窗口达标请求每秒也不能用于宣称可持续容量。 |

前轮报告补充口径勘误，保留原始数值。`power_of_two` 的缓存 0% 为请求级比例中位数，不能写作从未命中。前轮高载 TTFT 达标数为 140/200 与 182/200。原“1.673 vs 2.612 req/s”采用包含排空的时长作分母，注明原算法，另外用统一固定发送窗口重算。它不直接表示最大可持续容量。

失败统计采用互斥主状态并保留原因，包括完整成功、429 拒绝、HTTP 错误、超时、200 后流中断、质量失败和截断。汇总同时给请求执行成功率及质量通过率，避免同一请求被多个错误类别重复计入合计。

## 5. 验收与交付

- 性能沿用原门槛。稳定前缀缓存命中提高、续轮 P95 至少改善 **15%**。混合高载整体 P99 回退不超过 **10%**，固定窗口完整延迟达标请求每秒下降不超过 **5%**，执行失败/超时/拒绝合计比例增加不超过 **1 个百分点**。三组中至少两组通过且合并结果通过。保留 TTFT 达标指标与前轮对照。
- 真实 Agent 验收单独报告。历史回放至少满足高载延迟与错误率护栏。闭环任务不得出现由错误路由或协议变化造成的新增失败，列出逐任务完成时间和测试结果。真实任务若没有足够可缓存前缀，明确记录该分布与收益，不据此删题。
- 两策略故障与恢复均达到上述 20 秒目标，摘除后无新请求落到故障端，恢复后两台可接单，取消和断流无永久遗留的 Router 在途计数。记录耗时分布和最坏值。
- 交付 `docs/qwen-dual-replica-retest-results.md`，包含配对结果、逐项验收、缓存和吞吐勘误、数据集版本与哈希、原始记录位置、故障时间线、真实 Agent 逐任务结果和 Gemma 恢复检查。测试集与评分/回放程序另作为可复用交付。
- 任一项证据缺失就标记未验证，列出原因。收益与护栏都满足后，推荐进入 GLM 多副本隔离复测。GLM 参数需重新校准。

本计划中的 900 个高载样本、真实任务数量、20 秒故障目标和完整延迟预算流程，是为本轮升级回测选定的实验要求。它们作为数据集及 profile 的版本化内容保存。
