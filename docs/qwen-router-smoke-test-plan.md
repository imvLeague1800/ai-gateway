# Qwen Router 快速回归与单机并发测试计划

由执行 agent 在隔离测试环境运行。先用快速子集检查 Router 功能，再直连一台 Spark 测 Qwen 的 1–4 路并发。快速回归目标为每种策略 5–10 分钟。全量验收继续使用现有版本化测试集。 [测试资产](../benchmarks/router/README.md) · [完整验收计划](qwen-dual-replica-retest-plan.md)

## 1. 固定快速子集

从 `benchmarks/router/cases.jsonl` 和 `sessions.jsonl` 选 **16 个完整会话**，默认按下表挑选。若当前版本缺少某个 ID，从同类会话选取并记录替代原因。保留父轮、后续轮、工具定义、预期输出和评分方式。

| 来源 | 会话数 | 覆盖 |
| --- | ---: | --- |
| `qa-000` 至 `qa-003` | 4 | 独立短请求、显式模型入口和正确回复 |
| `agent-000` 至 `agent-003` | 4 | Agent 冷首轮、工具名和参数、带工具结果的稳定前缀续轮 |
| `rag-000` 至 `rag-003` | 4 | 约 16K 冷文档和同文档热续轮 |
| `rag-004` 至 `rag-007` | 4 | 复用原 RAG 会话，在第二轮前部替换召回内容，同时更新预期答案，验证返回新文档中的值 |

冻结这 16 个来源会话，约 **28 个计分请求**。用独立的 `benchmarks/router/smoke.json` 保存会话 ID、来源 manifest SHA-256 和变体规则。召回变化用衍生 ID 并记录原 ID。全量 `cases.jsonl`、`sessions.jsonl`、预算和回放配置继续作为完整验收基线。路由快测的负载与结果写入独立运行目录，避免与全量结果混算。

## 2. 路由快速回归

1. 核对两副本健康、版本及实际模型。使用同一入口分别跑 `power_of_two` 和 `cache_aware`，沿用当前隔离配置。换策略时排空在途请求，使用结构和 token 长度等价的新前缀标记，记录策略顺序和实际副本。
2. 先跑核心质量和缓存用例。对照冷首轮、稳定前缀续轮和前部召回变更，采集引擎缓存命中。途经 Router 的逐请求副本不可归因时标为未知。前缀命中判断使用实测缓存 token。
3. 从现有短 Agent/RAG 复用请求，另做一次短突发以触发隔离入口的排队，分别取消一条等待请求、一条已开始生成的请求，确认队列和在途计数恢复。副本不可用路径走 mock 或隔离 Router 摘流，核实健康副本可接单。若测试入口没有排队或取消指标，标记未验证并注明入口。
4. 快测通过条件为计分用例质量及协议符合预期、两副本都可服务、稳定前缀续轮观察到缓存复用、召回变更返回新值，以及能够观察的排队、取消、摘流行为符合配置。每类报告样本数、TTFT P50、最慢请求及失败原因。此样本量用于发现明显回退，P99 验收沿用全量计划。

## 3. 单机并发测试

直连 `.15` 的单个 Qwen 副本，保持当前权重、量化、模板、thinking 关闭、256K 上限、prefix caching、`max-num-seqs=4` 及 `max-num-batched-tokens=8192`。记录实际值，确认测试期间没有其他负载。独立运行以下三类请求，每类测 **1、2、3、4 路**。

| 场景 | 输入与缓存控制 |
| --- | --- |
| **短 Agent** | 保留现有短 Agent 的输入结构和上下文长度。增加需要生成较长代码或说明的独立派生用例，验证输出质量。 |
| **16K 冷文档** | 渲染后约 16K token。每路各用独立前缀标记，每档换标记，检查缓存命中接近冷基线。 |
| **16K 热续轮** | 给每条会话先发对应首轮预热，等首轮完成后再同时发续轮。预热请求排除在正式测量之外，记录每组实际缓存命中。 |

- 输出速度用例以实际生成 **约 256–512 token** 为目标，统一请求上限和采样配置。保留短输出、截断和失败样本及原因。分列各档输出长度分布，避免把输出长度差误当成并发效果。
- 每个场景及并发档先做 **3 轮同步突发**，每轮在统一起跑信号后发出该档所有请求。再做 **30 秒持续发送**，完成一条补一条，维持目标在途数。记录引擎实际 running 和 waiting。冷请求的输入每次换新标记。热请求轮换已预热的会话前缀，使用固定的上下文形态。
- 持续测量前先让该档负载进入稳定运行，记录测量窗口起止、窗口外排空和实际在途。使用可按窗口归因的输出 token 计数。若只能获取每条完成时的 usage，就单独报告整批总输出 token 除以首请求发出至最后一条结束的时间，并标为**整批吞吐**。

## 4. 记录、判断与交付

| 指标 | 计算与汇总 |
| --- | --- |
| **TTFT** | 客户端发出请求至首个非空正文或工具增量，报告逐条值、P50 和最慢值；样本足够再报 P95。有引擎指标时另记排队和 prefill。 |
| **每路输出 TPS** | 对至少输出两个 token 的流，用首 token 后的输出 token 数除以首 token 到最后输出的时间。记录每条输出 token 数、逐条 TPS 和中位数，样本足够再报 P10。标明客户端时间戳的测量口径。 |
| **整机输出 TPS** | 相同测量窗口内所有流的实际输出 token 总数除以窗口时长，附实际生成并发和分母；同步突发另报整批吞吐。 |
| **辅助数据** | 记录实际模型及副本、请求 ID、场景、并发、输入长度、缓存 token、完成时间、失败、截断、KV 使用率及抢占（如可取得）。 |

交付 `docs/qwen-router-smoke-test-results.md`，附快速子集清单、逐请求记录和下表。标明使用的数据集与脚本版本、配置、各档样本数、快测总耗时。原始记录放到独立运行目录，并在报告给出路径。

| 场景 | 并发档 | 样本数 | TTFT P50 / 最慢 | 每路 TPS 中位数 / P10（如足够） | 整机 TPS 或整批吞吐 | 缓存命中 | 失败 / 截断 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 待填 | 1–4 | | | | | | |

优先比较 **2 路和 3 路**。先按各场景可接受的 TTFT 和每路 TPS 判断，再比较整机 TPS。暂缺体验目标时，将 3 路整机增益至少 **10%** 作为筛选线，并列出相对于 2 路的体验代价。若主要回退来自长冷文档，下一轮单独验证长冷请求并发限制。快测筛出候选后，再用同一到达节奏走双副本实际入口，最终验收使用全量基线。
