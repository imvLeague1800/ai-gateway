# Qwen 长冷 RAG 补测与代码收敛计划

执行者接手两项工作。先将网关产品代码收敛到第一版并保留现行快测和压力测试，再用第一版已有的准入能力测长冷请求上限。两项分别提交，方便独立审查。验收基于 [单机快测结果](qwen-router-smoke-test-results.md) 中 2 路交互并发的起始建议。

## 实现原则

- 每轮测试先检查现有入口、配置和共用代码。优先通过现有参数完成实验，其次在原入口上修正缺陷或补齐参数。两种长冷上限使用同一套回放逻辑，由配置切换。
- 沿用 Scheduler 的总并发和长请求准入，以及现有测试的请求发送、用例生成和统计逻辑。比如稳态 TPS 的采集有缺口，就在已有测量流程里补齐窗口计数，让后续回测使用同一口径。
- 只有现有入口缺少所需能力，而且无法通过小改动补齐时，才新增代码。将新增逻辑放到最直接的现有模块里，保持控制流简单。多个入口确实需要同一段逻辑时，复用一个实现。
- 提交前检查改动是否简洁，删掉本次产生的临时脚本、重复实现和未使用的参数。交付说明列出复用了哪些功能，以及新增代码解决的具体缺口。

### 清理与验收顺序

1. 记录 `git status`、已跟踪 diff 和未跟踪文件清单。为将恢复或移除的实验文件保留可恢复快照，覆盖未跟踪源码。用逐路径变更执行清理，保留原提交历史。跳过 `.bak`、私密配置、`.verification/` 原始记录、已有报告及数据卷。
2. 更新活动测试入口和部署文档的引用。保留历史 Router v2 文档作为实验记录，将其部署入口标为退役。审查 `docs/local-test-deployment.md` 的现有差异，保留仍准确的实测资料，清理失效的 Auto 操作说明。
3. 核对测试脚本的 import、CLI、manifest 和 README 链接。从仓库运行第一版 Scheduler 的现有 CI 检查、数据集 validate 与保留的 mock 测试，检查当前 quick/full 两套测试可从单一文档找到入口。测试资产变更涉及 manifest 哈希时，另记版本和哈希，保留已归档 run 指向的旧指纹。逐项列出保留、删除和仍有依赖的文件。

## 2. 部署与对照配置

1. 核对 `.15` 当前 Qwen 的模型权重、量化、引擎版本、tokenizer、模板、缓存和启动参数。把 `.16` 从 Gemma 切换到与 `.15` 一致的独立 Qwen 副本。先检查原 Gemma 入口及依赖，记录其可用性变化，并留存 Gemma 启动配置作历史备份。**测试完成后 `.16` 保留 Qwen，原 Gemma 服务本轮停用。** 核对两台模型名称、256K 上限、prefix caching 和健康状态，报告最终端点。
2. **主对照固定到 `.15` 单副本**，保留 `.16` 给后续双副本验证。用第一版 Scheduler 的独立测试实例实施准入，不叠加其他副本选择组件。固定每副本 `max_concurrent_requests=2`，两组只改变 `max_long_requests=1` 或 `2`。复用现有的 `long_request_threshold_tokens`，两组均设为 8192，实测重渲染后的短 Agent 在阈值内，16K 文档超过阈值。此处所有超阈值样本都是冷文档，所以长请求上限可以代表长冷上限。带热前缀的长请求属于后续验证。
3. 引擎沿用快测配置 `max-num-seqs=4`、`max-num-batched-tokens=8192`、256K 与 prefix caching。所有测试请求关闭 thinking、固定采样和输出预算。固定客户端连接模式、认证、队列容量及截止时间。确保每 Key 的活动上限和压测客户端并发都不会把总准入压低到 2 以下。

## 3. 重放与指标

- 从快测派生用例复用**短 Agent 和约 16K 冷文档**，以相同评分和输出预算覆盖约 256–512 个输出 token。默认按请求数 **1:1 混跑**，在运行记录标明这是合成混合比例。两组使用同一到达时间表、输入及输出长度目标。冷文档每请求使用不同且等长等结构的早期前缀标记，验证实际缓存接近冷基线。固定并报告 Agent 缓存状态。
- 先用短预演选一个能让 16K 冷文档出现排队、又能在窗口内稳定处理的负载。正式测试采用冻结的开放环到达表，保持两个配置具有相同的到达压力。每组先预热至流量稳定，再测至少 **120 秒**，结束后停止注入并排空。做 **3 组配对回放**，交替先跑上限 1 和 2。报告每组实际发送率、各类样本数、队列趋势和排空耗时。
- 逐请求保存请求 ID、场景、实际后端、客户端发出时间、第一实质输出时间、最后输出及流结束时间、输出 token、缓存计数、失败和截断。**按短 Agent 与冷文档分别报告** TTFT P50/P95、每路 TPS P50/P10、网关排队 P50/P95、可获取的引擎排队 P50/P95 和完成时间。两级队列时间分开；缺逐请求证据时标记未知。每路 TPS 用首 token 之后的 token 数除以首 token 到最后输出的时长。
- **整机 TPS 按稳定窗口内实际生成的所有输出 token 除以窗口秒数**。首选引擎输出 token 单调计数器的区间增量，先用跨窗口长流确认计数在生成中持续推进。若计数只在请求结束时更新，使用可靠的逐 token 时间记录。SSE chunk 数不能直接当 token 数。取不到实际窗口计数时，将稳态整机 TPS 标为未验证，另报含排空的整批吞吐与分母。跨越窗口结束的流，其窗口内已生成 token 计入稳态指标。
- 采集每副本 running、waiting、长请求在途数、缓存、KV 使用率与抢占。确认两配置实际达到总在途 2，长文档叠加时分别受 1 和 2 的上限约束。附各类实际输出长度与成功率，检查性能差异是否受输出长度变化影响。
