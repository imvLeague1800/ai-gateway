# 双 Qwen 副本路由对照测试

> 执行结果见 [qwen-dual-replica-test-results.md](qwen-dual-replica-test-results.md)。

在隔离环境用同一批流量比较 vLLM Project Router 的 `power_of_two` 和 `cache_aware`。验证稳定前缀能否降低续轮 TTFT，以及热副本拥堵时能否及时把请求派往另一台。测试范围为 Spark `.15`、`.16` 和隔离网关。

## 1. 部署与回退

1. 记录 `.16` 的 Gemma 镜像或服务版本、权重路径、启动参数、环境变量来源、端口和网关映射。保留可复用的原始启动配置及权重，在记录中写明停止 Qwen、启动 Gemma、恢复网关映射的步骤。使用现有私密配置保存凭据。
2. 停止 `.16` 的 Gemma，在 `.16` 启动与 `.15` 一致的 Qwen3.6-35B-A3B-NVFP4。两台各运行一个独立副本。对齐权重版本、量化、vLLM 版本、tokenizer、聊天模板、prefix caching 和引擎并发参数。两台保持 `max_model_len=262144`，测试网关上下文同为 `262144`。负载用流式请求、`temperature=0`、最多 1,024 个输出 token，并按前轮已验证的方式显式关闭 thinking。核实实际生效配置。 [前轮实测](qwen-gemma-256k-test-results.md)
3. 分别直连两台跑短问答和冷、热 16K 文档样例。确认响应质量、模板、缓存指标和时延可比。若任一端无法健康启动、配置不一致，或相同场景的中位 TTFT 相差超过 15%，先定位差异，再开始策略对照。若 `.16` 无法恢复到可测状态，执行 Gemma 回退。
4. 采用同一镜像版本的 vLLM Project Router `v0.1.17`，记录实际镜像 digest。暴露一个测试模型别名，两台作为同模型池的两个 worker。由 Router 独自负责选副本。若测试入口保留 LiteLLM，则只转发到一个 Router 入口。确认测试路径没有第二个组件按物理副本选址或重复计账。正式回放前，逐请求关联 Router 决策或引擎访问日志，确认能识别实际副本。 [版本说明](https://github.com/vllm-project/router/releases/tag/v0.1.17) · [策略文档](https://github.com/vllm-project/router/blob/v0.1.17/docs/load_balancing/README.md)
5. 测试结束后停止隔离 Router、移除临时测试映射，并恢复 `.16` Gemma。用健康检查、模型列表和一条原入口短请求确认恢复。生产网关、生产副本分配和 Auto 规则留在本轮范围之外。

## 2. 压测场景

| 场景 | 执行方式 | 核对点 |
| --- | --- | --- |
| **A. 独立代码问答** | 短请求独立生成。提示前部带会话标记，避免形成足以命中的共同前缀。 | 两台都有有效请求，短请求无持续积压。 |
| **B. 稳定前缀** | 回放 16K 同文档追问和真实多轮编码 Agent。Agent 重复前缀应至少覆盖两个经实测可缓存的块。首轮冷启动，续轮保留同样的间隔和前缀。每轮同一会话按顺序发起。 | 续轮命中已预热的副本，实测缓存 token 增多，TTFT 下降。首轮和续轮分开报告。 |
| **C. 混合峰值** | 无代表性流量记录时，按请求数用 40% 多轮 Agent、30% 独立代码问答、30% 长文档/RAG。RAG 一半沿用文档，另一半变更前部召回内容。用固定到达时间的开放环回放，设轻载和高负载两档。 | 缓存收益在混跑时是否仍存在，冷请求和短请求的尾延迟、队列和达标吞吐是否回退。 |
| **D. 热副本偏忙** | 先通过 Router 预热一个副本并确认它持有前缀。优先用经 Router 派发的背景长请求制造负载差。若需直连注入背景流量，先确认 Router 的实际负载信号能看到该负载。另一台保持有余量。重做一轮并交换两台角色。 | 记录何时改派、实际负载和重新 prefill 的代价。确认热副本忙时，另一台能及时接单。 |
| **E. 副本故障与恢复** | 单独从测试池摘除或停止一个 Qwen 副本，再恢复。分别测试已有请求、新请求和恢复后的请求。 | 在配置的检测窗口后停止向故障端派新请求。健康端继续接单。恢复可观测，并记录在途失败、重试和容量恢复。 |

先用 `power_of_two` 短扫确定固定请求率。轻载取不出现持续排队的档位，高负载取出现可测排队且还能稳定处理的档位。记录实际请求率和并发。用小规模预演为 `cache_aware` 校准负载偏斜阈值。双副本池的默认绝对差 32 可能偏大，选择能让场景 D 触发改派、场景 B 保留亲和的配置，记录参数并冻结。正式回放期间，两策略使用同一到达序列、请求内容、入口限流和后端配置。

性能场景做至少三组配对回放，交替策略顺序。每组开跑前排空在途请求，清理 Router 的前缀历史，使用两策略等价、与旧轮次隔离的前缀标记，再按相同步骤预热。混合峰值场景每种策略至少收集 300 个请求，再比较整体 P99。各子场景小样本一并列原始值。故障场景单独统计。

## 3. 指标和交付

- **逐请求记录**包括策略、场景、轮次、到达时间、会话标记、实际副本、输入和输出 token、TTFT、完成时间、可获取的缓存 token、状态码、质量判定和错误。TTFT 以客户端看到的首个实质流式增量为准。并发时仅有引擎聚合计数，就按副本和测试窗口报告缓存命中，不做单请求归因。
- **逐副本记录**包括派发数、运行和等待请求、可获取的引擎队列时间、KV 使用率、缓存命中及查询 token、抢占重算和故障摘除时间。分别记录实际送入的、成功的、失败的、超时的和被拒绝的请求。
- **聚合交付**包含以下对照表、逐请求数据、最终配置与镜像 digest、场景 D/E 时间线，以及 `.16` Gemma 恢复检查结果。按场景和负载档位给样本数。固定回放窗口内，达标吞吐按每秒成功、质量通过且符合预先冻结延迟预算的请求数计算。用试跑基线为各场景确定预算，并在正式回放前写入记录。 [vLLM 指标说明](https://docs.vllm.ai/en/stable/usage/metrics/)

## 4. 验收与决策

- **功能必过。** 两策略均能在两副本上完成正确的流式和工具请求。场景 B 能确认实际命中副本。场景 D 能观察到偏忙时向空闲副本派发。场景 E 在检测窗口后无新请求发往失效副本，恢复后可重新接单。测试结束后 Gemma 可从原入口调用。
- **推荐带 `cache_aware` 到 GLM 复测的门槛。** 场景 B 的缓存 token 占比提高，且续轮 P95 TTFT 相对 `power_of_two` 至少下降 **15%**。场景 C 高负载的整体 P99 TTFT 回退不超过 **10%**，达标吞吐下降不超过 **5%**，失败、超时和拒绝合计比例增加不超过 **1 个百分点**。至少三组配对回放中的两组达到这些门槛，并且合并结果也达标。以上是本次试验的决策阈值。
- **未达标时保留 `power_of_two` 作为基线。** 报告主要原因。缓存数据缺失、实际副本无法归因、P99 样本不足或对照条件未对齐时，将相关结论标为证据不足。双 Qwen 结果用于选择后续 GLM 测试候选，GLM 多副本收益由该池实测决定。
