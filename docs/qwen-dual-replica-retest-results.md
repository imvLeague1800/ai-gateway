# 双 Qwen Router 补测与可复用测试集结果

测试日期：2026-11-23。执行范围：Spark `.15`、`.16` 和隔离 vLLM Router。生产 Gateway/Scheduler 配置、Auto 规则和模型副本分配未改动；`.16` Gemma 在测试期间临时替换为第二个 Qwen，测试结束后恢复。真实 Agent 语料未提供，按计划将该项标为待补，不用合成样本冒充真实来源。

## 结论摘要

- **数据与校准**：`benchmarks/router` v1.2.0，300 个冻结计分用例/195 会话，独立校准集 60 例；数据集校验、mock 状态/缓存/百分位校验和 60/60 校准全部通过。真实 Agent 会话为 0，该项待补。
- **稳定前缀（B）**：3/3 组达标。合并后缓存 token 占比 **32.6% → 44.8%**，同副本续轮 **83/118 → 116/116**；Agent 续轮 P95 **1,493 → 337 ms（-77.4%）**，RAG 续轮 P95 **2,936 → 2,154 ms（-26.6%）**；冷首轮 TTFT 两策略相近。
- **混合高载（C，2.0 req/s）**：3/3 组达标。合并 P99 **9,871 → 5,940 ms（0.602×）**，固定窗口完整延迟达标 RPS **0.906 → 1.390（1.534×）**；TTFT 达标 **731/900 → 883/900**，完整延迟达标 **530/900 → 813/900**；执行失败/超时/拒绝均为 0；高载峰值 waiting 13→6。
- **轻载（1.5 req/s）**：合并 P99 **5,178 → 3,845 ms**，固定窗口达标 RPS **1.181 → 1.223**，缓存 **32.3% → 44.8%**；每策略 900/900 成功（3 组 × 300）。
- **故障/恢复（E）**：12/12 周期完成。检测中位 11.64s、最大 11.76s（目标 ≤20s）；Router 在引擎 `/health` 恢复后中位 7.15s、最大 19.3s 重新接单（目标 ≤20s）；摘除后与恢复后的 20 个探针均为 200，`running_after` 两侧为 0。24/48 个在途请求在停止副本上中断，24 个在健康副本完成；HTTP 200 后断流单独计失败。
- **热副本对照**：`cache_aware` 在 `.15` 热时把自动探针改派 `.16`（3,001ms，冷）；强制等待 `.15` 为 381ms、缓存 94.6%。`.16` 热时自动探针改派 `.15`（2,884ms）；强制等待 `.16` 为 349ms、缓存 94.6%。双向都观察到改派，强制等待以 3 个背景长请求留在热副本为代价。
- **真实 Agent**：待补；未用合成记录替代。
- **恢复**：`.16` Gemma 已恢复（`max_model_len=262144`，健康，短请求 200 “OK”），生产 Gateway 经原入口返回 200；`.16` `.env` 已还原，测试 Router 已移除，`.15` Qwen 健康，SSH 隧道已关闭。

## 前轮报告勘误

1. **`power_of_two` 缓存 0% 不是“从未命中”**：前轮 B 表写的是逐请求缓存比的中位数；`power_of_two` 有 5/12 续轮与父轮同副本并产生非零缓存命中，只是中位数为 0。正确表述应为“请求命中比例中位数为 0；同副本续轮 5/12；窗口 token 命中占比见本次重算”。
2. **前轮高载 TTFT 达标数**：`power_of_two` 为 **140/200**，`cache_aware` 为 **182/200**（前轮 C 高载 4 组合并），不能只看聚合 RPS。
3. **前轮 “1.673 vs 2.612 req/s” 含排空**：分母包含窗口结束后的排空时间，不是固定窗口 RPS，也不代表最大可持续容量。本次按冻结窗口重算，并单独报告 `drain_s`、固定窗口完整延迟达标 RPS 和 TTFT 达标 RPS。
4. **前轮缓存中位数口径**：并发窗口只有引擎聚合计数，前轮部分 0% 是请求级中位数；本次报告统一给出窗口 `hits/queries` token 占比和请求级同副本比例（stable 有逐请求归因）。
5. **QA 用例修正**：v1.1 的 `17*23` 问题在 Qwen 上稳定被答成 `401`（与路由无关），v1.2 改为 `2+2` 并重新生成；旧 v1.1 数据保留在 `.verification/dual-qwen/retest-calibration/` 供审计。

### 热副本强制选址对照

在 `cache_aware` 下先预热目标副本并制造 3 个 Router 可见的长请求，再配对：
- **自动改派**：Router 把带热前缀的新请求送到空闲副本（重新 prefill）。
- **强制等待热副本**：客户端直接向热副本发起同一请求，保持热前缀缓存；该入口单独标记，不代表生产建议。

| 热副本 | 背景负载 | 自动落点 / TTFT / 完成 | 强制落点 / TTFT / 完成 | 强制缓存 |
| --- | --- | --- | --- | ---: |
| `.15` | `.15`=3 | `.16` / 3,001 / 3,147 ms | `.15` / 381 / 620 ms | 94.55% |
| `.16` | `.16`=3 | `.15` / 2,884 / 2,976 ms | `.16` / 349 / 500 ms | 94.58% |

- 双向都观察到自动改派；强制等待热副本可把 TTFT 从约 2.9–3.0s 降到约 0.35–0.38s，但会让 3 个长请求继续压在热副本上。该项只作为阈值分析，不改变 Router 的自动负载均衡策略。

3. **高载速率与到达漂移**：3.0 req/s 在当前环境过载（P50 21s、峰值 waiting 73、QA 质量失败），因此按计划先校准为 2.0 req/s；high 结论是 2.0 下的对照，不是最大可持续容量。续轮等待父步骤完成后才发送，实测 high 到达率为 p2 1.907、ca 1.974 req/s（计划 2.0），light 为 1.483/1.489；p2 的到达率略低是它更慢的结果，固定窗口仍是预生成的 195/245s，排空单独记录且本次 `drain_s=0`。
4. **前缀隔离**：vLLM 无 prefix-cache reset 接口；每个 run 使用随机中性 namespace，不绑定策略名。两策略请求结构等价但字节不完全相同；稳定前缀有逐请求 worker 归因，高/轻载只有窗口级引擎与 Router 归因。稳定 profile 中 ca 4 个、p2 2 个续轮因 metrics 竞态未归因。引擎没有暴露逐请求 cache hit 计数，因此不报告请求级缓存命中比例；请求级证据只用于同副本续轮归因，缓存收益统一用窗口 token 占比。
5. **故障恢复证据**：3 个 `cache_aware` 恢复周期中，20 个探针全部被亲和到另一台，目标副本的 Router 接单未被直接覆盖；目标引擎 `/health` 已恢复，后续周期和热实验证明其可接单，故标为部分证据。
6. **Router 负载信号**：Router 的 `/get_load` 仍为 404（vLLM 暴露 `/load`），只使用本地在途计数；绕过 Router 的直连负载不可见。热副本强制等待对照因此使用单独的直接入口，不能与 Router 自动入口混算。
7. **生产影响**：故障矩阵 6 次停止 `.15` 生产 Qwen、6 次停止 `.16`；测试前 24 小时生产 Scheduler 无准入请求，生产 Gateway/Scheduler 配置和 Auto 规则未改。`.16` Gemma 已恢复并通过原入口验证。
8. **预算冻结**：TTFT 沿用前轮预算，完成时间预算来自 60 例独立校准集，正式验收未回调；任何未达标样本保留在原始记录中，没有被低延迟样本替代。
9. **原始证据持久化**：大文件仍在执行机 `.verification/dual-qwen/`（Git 忽略），尚未迁入公司内部持久存储，也未设定正式保留期；路径和 SHA-256 已登记，迁移后需按清单复核。
